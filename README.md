# Мессенджер в стиле Telegram

Внешний вид и поведение приближены к Telegram: список чатов слева с превью
последнего сообщения, переписка — классическими пузырями (свои сообщения
справа, зелёно-белые, чужие — слева, белые), поиск по чатам, статус
"печатает…" в шапке, галочки прочтения.

## Как запустить в VS Code

1. Установи Node.js: https://nodejs.org (LTS)
2. Открой папку `chat-app-tg` в VS Code
3. В терминале (Ctrl + `):
   ```bash
   npm install
   npm start
   ```
4. Открой в браузере: `http://localhost:3000`

## Проверить с "двумя аккаунтами"

Открой обычную вкладку и приватное окно браузера, зайди под разными именами —
сообщения будут приходить друг другу мгновенно.

## Что реализовано

- Список чатов с аватарами, превью последнего сообщения и временем
- Поиск по чатам (фильтрация в реальном времени)
- Пузыри сообщений: свои — справа, чужие — слева
- Группировка сообщений одного автора подряд (аватар только у последнего)
- Галочки "прочитано" на своих сообщениях
- Индикатор "печатает…" в шапке чата (можно отключить в настройках)
- Счётчик непрочитанных сообщений на чатах, которые сейчас не открыты
- Создание новых чатов
- Тёмная/светлая/системная тема, акцентный цвет, фон переписки, размер шрифта
- **Один аккаунт на устройство + внутренний Nova ID**
- **Пароль на аккаунте** — вход требует пароль (хранится только как scrypt-хеш), а не только `deviceId`; после нескольких неверных попыток — временная блокировка
- Смена юзернейма в Настройках → Аккаунт (без создания нового Nova ID)
- **Уникальный юзернейм (@username), как в Telegram** — сервер не даст занять юзернейм, который уже используется другим аккаунтом
- Выход из аккаунта (Настройки → Аккаунт → «Выйти из аккаунта»)

## Как работает привязка "один аккаунт — одно устройство"

Это демо-проект без базы данных и без настоящей SMS-регистрации, поэтому
"телефонные номера" здесь — не настоящие: это просто внутренний
идентификатор аккаунта, **Nova ID** (вида `NOVA-482913`), который сервер
генерирует и выдаёт при первой регистрации.

Как это устроено:

1. При первом заходе браузер генерирует случайный `deviceId` и сохраняет
   его в `localStorage`. Это "устройство" в терминах приложения — оно
   определяет, к какому аккаунту вообще можно попытаться войти с этого
   браузера, но **само по себе доступ не даёт**.
2. При регистрации/входе клиент отправляет на сервер `{ name, deviceId,
   password }`. Сервер смотрит, есть ли уже аккаунт с таким `deviceId`:
   - если аккаунта нет — создаёт новый, выдаёт ему уникальный Nova ID и
     сохраняет **хеш** введённого пароля (scrypt + соль, сам пароль
     нигде не хранится и не логируется);
   - если аккаунт уже есть — сервер проверяет пароль. Совпал — логинит;
     не совпал — отклоняет вход и увеличивает счётчик неудачных
     попыток (после нескольких подряд — временная блокировка
     аккаунта на этом устройстве).
3. Пароль **не сохраняется в браузере** и не подставляется
   автоматически — при каждом новом заходе (после закрытия вкладки)
   его нужно ввести заново. Автоматически подставляется только имя.
4. Nova ID и текущее имя видны в Настройках → Аккаунт; там же можно
   переименовать свой аккаунт (это не создаёт новый — тот же Nova ID
   остаётся).

**Почему это важнее, чем просто `deviceId`:** раньше владение строкой
`deviceId` (например, украденной из `localStorage` через XSS, чужой
браузер на общем компьютере или скопированной по ошибке) само по себе
означало полный доступ к аккаунту — без пароля сервер логинил
кого угодно. Теперь `deviceId` без пароля бесполезен: он лишь
указывает, какой аккаунт закреплён за этим браузером, а войти в него
может только тот, кто знает пароль.

**Важно:** это по-прежнему демо-проект без базы данных — при
перезапуске сервера все аккаунты и пароли теряются (это просто
in-memory `Map`, не постоянное хранилище). Если очистить хранилище
браузера, открыть режим инкогнито или зайти с другого устройства,
сервер увидит "новый" `deviceId` и предложит зарегистрировать новый
аккаунт с новым паролем — восстановить доступ к старому аккаунту
с другого устройства сейчас нельзя (нет привязки к email/телефону).
Для полноценной защиты в продакшене нужны: постоянная база данных,
восстановление пароля, HTTPS/WSS и (если это должно заменять
телефонную регистрацию, как в Telegram) настоящая SMS/email-верификация.

## Дальше можно добавить

- Настоящую базу данных и полноценную серверную защиту аккаунтов
- Реальную SMS/email-верификацию, если нужен production-уровень
- Личные (приватные) чаты 1-на-1, отдельно от групповых
- Голосовые сообщения, реакции
- Пересылку сообщений, ответы (reply), редактирование/удаление
